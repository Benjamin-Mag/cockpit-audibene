# Cockpit Audibene — guide pour les agents

Extension Chrome/Edge (Manifest V3) : un panneau latéral à côté de Salesforce pour un conseiller audibene. Elle a remplacé cinq extensions et deux sites. Propriétaire : Benjamin Magnier (conseiller, non développeur — lui parler en français, sans jargon, et viser toujours **le moins de clics possible**).

> **Deux dispositions depuis le 2026-10-01.** `main` porte le design **Fusion** (versions 1.1.x : barre de navigation en bas, écran Fiche, Réglages derrière la roue, édition plein écran). La branche **`classique`** garde l'ancienne disposition (onglets en haut, versions 1.0.x) : elle reste proposée aux collègues en parallèle (`cockpit-audibene-classique.zip`), et les correctifs non liés au design doivent y être reportés (cherry-pick).
>
> **Deux projets depuis le 2026-09-22.** Ce dépôt est la version d'équipe. Benjamin a sa copie privée **Cockpit Benjamin** (`Benjamin-Mag/cockpit-benjamin`, dossier `ProjectsCockpit Benjamin`, icône orange, versions 2.x) qui garde la page Ventes. **Depuis le 2026-10-20, Cockpit Benjamin est lui aussi en nouveau design** (v2.1.x, Ventes derrière une icône € à côté de la roue) : les corrections lui sont reportées depuis **`main`** (`git fetch upstream && git merge upstream/main` dans son dossier), plus depuis `classique`. Rien ne remonte jamais de Cockpit Benjamin vers ce dépôt.

## Règles non négociables

1. **`main` est réservé au chef d'orchestre** (la session « projets-b4 »). Tout autre agent travaille sur une branche, ouvre une Pull Request et envoie un rapport ; le chef d'orchestre relit, teste, merge et publie. Ne jamais pousser sur `main`, ne jamais créer de tag.
2. **Ne jamais modifier les anciens repos** (`Générateur de mail`, `Suivi Ventes Primes`, `Colleur*`, `Extension Message Vocal`) : les collègues les utilisent encore. Lecture seule, comme référence.
3. **Pas de `confirm()` / `alert()` / `prompt()`** : bloqués dans un panneau latéral. Utiliser `DeleteBtn` (deux temps) et les toasts.
4. **Rien d'identifiable dans le dépôt** (il est public) : ni identifiant de fiche Salesforce (`00Q…`, `006…`), ni nom de patient, ni téléphone, ni e-mail, ni nom de partenaire réel, ni identifiant de rapport interne — y compris dans les journaux de `docs/`, les messages de commit et les Pull Requests. Pour un exemple, écrire « une Piste de test », « un centre partenaire ». Les vrais jeux d'essai restent en local.
5. **Aucune donnée ne quitte le poste** : pas de télémétrie, pas d'appel réseau — seules exceptions : l'ORL Finder interroge Doctolib avec les coordonnées GPS du code postal du patient (jamais son nom), et la page Partenaires demande à Doctolib ou à rdv.acuitis.com les créneaux libres d'un partenaire (rien du patient n'est envoyé). Les données vivent dans `chrome.storage.local` + `cockpit.json`.
6. Design : palette de l'ancien générateur (`--accent #1b4f9b`, fond `#eaf3fb`, Poppins), animations lentes et douces (≥ 280 ms), tout texte généré affiché dans un `EditablePreview`.
7. TypeScript strict, pas de commentaires explicatifs inutiles, commits en français avec le trailer `Co-Authored-By` du modèle Claude utilisé.

## Commandes

```bash
npm install
npm run build        # dist/ = extension non empaquetée (Edge/Chrome → mode développeur → charger dist/)
npm run dev          # aperçu du panneau dans un onglet (mode web, sans Salesforce) sur http://localhost:5173/panel.html
npm run build:site   # dist-site/ = page d'installation + version web
npm run zip          # release/cockpit-audibene.zip
npx tsc --noEmit     # vérification des types (à faire avant tout commit)
npm test             # banc d'essai Playwright : le vrai panneau dans un faux navigateur (Salesforce, Doctolib, Acuitis simulés) — voir tests/LISEZMOI.md
```

**Banc d'essai (depuis la v1.0.43)** : `tests/e2e/*.spec.ts`, faux navigateur `tests/e2e/faux-navigateur.js`, aides `tests/e2e/outils.ts`. Il teste le panneau, **pas** le script de page Salesforce. Données 100 % fictives (règle n°4). Plusieurs worktrees en même temps : donner à chacun son `PW_PORT`. Si le Chromium de Playwright n'est pas installé (`npx playwright install chromium`), utiliser le Chrome du poste : `CHROMIUM_PATH="C:/Program Files/Google/Chrome/Application/chrome.exe" npm test`. Tout correctif de comportement arrive avec un test qui échoue avant et passe après.

Tester dans un vrai Salesforce : `edge://extensions` → ↻ sur la carte de l'extension, puis F5 sur l'onglet Salesforce si le script de page a changé (le panneau ré-injecte normalement tout seul un script périmé grâce à l'identifiant de build).

### Protocole panneau ↔ page
Le panneau envoie des `ContentRequest` (`src/shared/messages.ts`) via `chrome.tabs.sendMessage` ; la page répond par un `ContentResponse`. Avant tout envoi, `ensureContent` ping la page et injecte `content.js` si absent ou périmé. Le contexte (Piste/Opportunité, composeur ouvert) est poussé par un port tant que le panneau est ouvert. `lirePartnerSearch` → `{ ok, msg, partenaires: PartenaireSF[] }` (lecture de l'onglet Partner Search, au clic seulement). Pour un cadre précis (application Canvas), `sendToFrame` + `chrome.webNavigation.getAllFrames` + permission d'origine demandée au clic (`optional_host_permissions`).

### Vocabulaire de Benjamin (à respecter dans l'interface)
- **COSI** = remplir les champs de l'onglet Anamnèse d'une Piste par puces (`views/Anamnese.tsx`). Les phrases enregistrées (mutuelles, loisirs, situations) sont communes à une situation, mais la saisie en cours et les phrases cochées appartiennent à l'emplacement (Situation 1 ou 2) : la même situation peut être choisie deux fois avec des commentaires différents (v1.0.48). Elles se réordonnent en glissant, comme les catégories de mails (pas de bouton de tri : Benjamin n'en veut pas). Sous une situation choisie, ces phrases sont des puces **un peu plus foncées** que les choix de situation (`.situation .sub .chip`, v1.1.2).
- **Anamnèse** = texte intro + résumé Salesforce collé + signature, écrit dans « Remarques générales profil client » (`views/Commentaire.tsx`).
- **Chat partenaire** = fil Chatter de l'Opportunité (`views/ChatPartenaire.tsx`). Pas de choix M./Mme : le genre vient de la fiche (v1.0.49).
- **Message vocal** = commentaire « MV » dans Commentaires internes + « Piste non joignable ».
- **Dupliquer un modèle** (Mails, icône copie à côté du crayon) = partir d'un modèle existant : copie avec un nouvel identifiant, titre « … (copie) », l'original ne bouge pas (v1.1.4).
- **Partenaires** = écran de la barre du bas sur une Piste (disposition Fusion ; onglet du sélecteur du haut dans la disposition classique) : partenaires de la Piste lus dans Partner Search, créneaux Doctolib des partenaires qui ont une page publique (test auditif, première consultation avec puis sans ordonnance), créneaux Acuitis pour les magasins Acuitis (bilan auditif et 1er rendez-vous), agenda Doctolib Pro ou autre site en bouton. Le « Commentaire Partnersearch » est lu (c'est lui qui porte les liens de RDV) mais **plus affiché** depuis la v1.0.39 : Benjamin n'en avait pas besoin à l'écran.
- **Hearo** = utilitaire SMS de la barre du bas (app Canvas, libellé variable : Hearo / Nouveau message / Approbation en attente).
- **ORL Finder** = onglet de la Piste, et de l'Opportunité depuis la v1.1.13 / classique 1.0.63 (après Mails et Chat partenaire ; code postal lu dans le titre de l'Opportunité ; la recherche ne part qu'à l'ouverture de l'écran) : ORL proches du patient (Doctolib) avec créneau visible, tri créneau disponible → secteur 1 avant secteur 2 → créneau le plus tôt → distance (v1.0.33), « pas de téléphone = pas de ligne », TOP 3, message type audiométrie, itinéraire Google Maps. « Trier par » (pertinence / plus tôt / plus proche, mémorisé), puces cumulables et recherche par nom ou ville : tout se fait sur les résultats déjà chargés (v1.0.34).

## Disposition Fusion (main, 1.1.x)
- Barre de navigation **en bas** (`<nav class="barre">`) : sur une Piste Fiche / COSI / Anamnèse / ORL Finder / Partenaires, sur une Opportunité Fiche / Mails / Chat partenaire / ORL Finder (v1.1.13) ; Réglages derrière la roue en haut à droite (second clic = retour). Les boutons sont désactivés tant que la page Salesforce n'a pas répondu, Réglages reste joignable. Juste avant la roue, l'**icône Outlook** (enveloppe, v1.1.14, d'abord dans Cockpit Benjamin v2.1.1) : copie le nom du patient chargé (Outlook de bureau : Ctrl+E puis Ctrl+V), affiche ou ouvre l'onglet Outlook web (`outlook.cloud.microsoft`, aussi reconnus `outlook.office.com`, `outlook.office365.com`) et y lance la recherche (`#topSearchInput` puis Entrée, `src/panel/outlook.ts`) ; autorisation demandée au premier clic (`optional_host_permissions` déjà là). Test : `tests/e2e/81-outlook.spec.ts`.
- Écran **Fiche** à l'ouverture : parcours de la fiche, carte par étape, « Reprendre » quand une saisie est en cours (`aUneSaisie`, les simples choix de navigation ne comptent pas). Hors écran Fiche, carte patient réduite (MV / SMS / Relire) — **sauf sur une Piste dans COSI et Anamnèse**, où il n'y a pas de carte du tout (v1.1.1). Dans ce cas l'en-tête collé en haut (« Salesforce » + roue) prend un fond plein et un trait fin dessous (`.top.trait`, v1.1.2), et c'est lui qui dit si le patient est lu (v1.1.8) : rond à gauche de « Salesforce » **vert** (lu, nom au survol), **orange** qui pulse (lecture), **rouge** (pas lu), et bouton ↻ « Relire la fiche » à gauche de la roue (`.relire`, masqué en édition plein écran). Sans ça, une lecture vide passait inaperçue et Doctolib proposait le patient d'avant. Une relecture demandée (↻) passe l'état en lecture même quand une fiche est gardée en mémoire. Le même rond existe dans la disposition **classique** depuis la 1.0.62 (sur toute fiche Salesforce ; le ↻ y est déjà dans la carte).
- **Dernier écran gardé par fiche** (`ecranGarde` / `garderEcran` dans `brouillons.ts`, champ `ecran` à part des saisies, seulement pour une clé `lead:`/`opportunity:`) ; hors fiche, seul Réglages est conservé.
- Édition **plein écran** d'un modèle (Mails, Anamnèse, Chat) : barre et roue masquées, sorties par Enregistrer / Annuler. Sur Doctolib/Acuitis/Grand Audition, la carte « Coller le patient » reste visible.
- Tests propres : `tests/e2e/50-fusion.spec.ts`, `70-relecture.spec.ts`. L'aide `aller(page, 'Réglages')` passe par la roue.

## Pièges Salesforce connus (ne pas réintroduire)
- Salesforce Console garde plusieurs fiches montées en même temps : toujours passer par `visibleEl` (taille rendue > 0) et **ne jamais retourner un candidat invisible** par défaut.
- **Une seule lecture de page par action** : le coût d'un `deepAll` vient de la traversée du shadow DOM (un appel navigateur par élément). Regrouper les recherches avec `deepGroup([...])` puis `valeurChamp(labels, ...)` (v1.0.33 : lecture de fiche 3 à 4 fois plus rapide).
- Shadow DOM : `.shadowRoot` d'abord, puis `chrome.dom.openOrClosedShadowRoot` (l'ordre inverse a déjà cassé la lecture).
- Chercher les éléments par **texte / titre / placeholder**, jamais par position ni référence gardée : Lightning re-rend après chaque clic.
- Un `<label>` créé par nous dans la page entrerait en collision avec la recherche de labels Salesforce : le panneau vit dans le side panel, pas dans la page.
- « Traitement médical » (liste double) refuse les clics scriptés (`event.isTrusted`) : reste manuel.
- Après « Enregistrer », attendre ~1,2 s avant le clic suivant (re-rendu).
- **Choisir le dossier doit toujours laisser une copie dans le navigateur** (`chooseFolder` → `localWrite`) : Edge retire l'accès au dossier dès que le panneau se ferme. Sans cette copie, une extension réinstallée rouvrait sur l'écran « prénom nom » avec un bouton « C'est parti » mort (v1.0.44, test `65-reinstallation`). Sans copie ni accès, l'accueil repropose le dossier (`needs-folder`).
- **Le navigateur recharge le panneau à chaque changement d'onglet** : aucune information ne survit dans une variable ou un `useRef`. Même principe pour les écrans qui interrogent le réseau (ORL Finder, Partenaires) : **réafficher d'abord ce qui est en cache, relancer ensuite seulement si c'est périmé, et sans vider la liste** (`CACHE_MS` = encore frais, `CACHE_VUE_MS` = encore affichable ; v1.0.42). Ce qui doit survivre va en mémoire de session (`brouillons.ts`) : les saisies, la dernière fiche lue (`ficheMemo`, réaffichée aussitôt, relue seulement si elle a plus de `FICHE_FRAICHE_MS`) et l'onglet Salesforce suivi (`ongletSfGarde`, sans lequel le panneau perdait la fiche en passant sur un site quelconque — v1.0.40).
- **Le panneau garde la dernière fiche Salesforce** quand l'utilisateur passe sur un site sans rapport (`ongletSf` dans `app.tsx`) : les actions visent cet onglet en arrière-plan. Toute nouvelle saisie dans un onglet du panneau doit utiliser `useBrouillon(ficheKey, 'ecran.champ', départ)` au lieu de `useState`, et un aperçu retouché passe `retouche` à `EditablePreview`.
- **Jamais de lecture `deepAll` périodique** (minuterie) dans la page Salesforce : parcourir tout le shadow DOM Lightning toutes les quelques secondes a figé Salesforce (v1.0.27, puis v1.0.32 : le suivi de contexte toutes les 0,8 s cherchait le composeur d'e-mail dans toute la page, coût proportionnel aux fiches gardées par la console, d'où des gels « de plus en plus » fréquents). Le port de contexte ne lit que l'adresse (`currentContext`). Les lectures lourdes se font au clic ou au changement de fiche.
- Le champ « Commentaires » des Commentaires internes n'est PAS l'anamnèse : l'anamnèse va dans « Remarques générales profil client » (rubrique Commentaire en bas de la Piste).
- Chatter : la zone « Partager une mise à jour… » devient un éditeur riche au focus ; taper via `execCommand('insertText')`, puis bouton « Envoyer un message ».
- **Les champs d'une fiche ne sont dans la page que si son sous-onglet est affiché** : sur « Partner Search », plus rien n'est lisible. `readFiche` passe alors sur le sous-onglet des champs (« Anamnèse » / « Détails », jamais un onglet portant un autre nom), lit **tout** — y compris le code postal — puis rend l'utilisateur à son sous-onglet (v1.0.40). Trois règles depuis la v1.0.45 : le sous-onglet à rendre est mémorisé **par son texte** et retrouvé au moment de revenir (`revenirSur`), jamais par élément gardé — Lightning reconstruit la barre après un clic et l'ancien élément devient muet ; les lectures qui changent de sous-onglet (`readFiche`, `lirePartnerSearch`) passent par `enSerie` pour ne jamais se croiser ; et la lecture de Partner Search reste **invisible** (règle ferme de Benjamin, v1.0.47) : le sous-onglet précédent est remis dès la lecture finie, et `revenirSur` attend que Lightning l'ait vraiment affiché avant de rendre la main, pour que la lecture suivante parte d'une barre stable.
- Composeur d'e-mail de l'Opportunité : boutons **Client / Partenaire** en haut (destinataire). Les mêmes libellés existent dans le formulaire de résumé d'appel : ne chercher le choix que dans le composeur, délimité par l'éditeur `.ql-editor` et son bouton « Envoyer » (`composerOf` dans `actions.ts`). Choisir le destinataire AVANT de remplir objet et corps. Juste après l'ouverture, les boutons arrivent après l'éditeur et Salesforce vide le corps en finissant son affichage : attendre, insérer, puis vérifier que le corps est toujours là.

## Piège Grand Audition (v1.1.9)
- Formulaire `rendez-vous.grandaudition.com` (React) : chaque bouton de civilité **M. / Mme** fait `setState({...état, civil})` avec l'état de son dernier affichage. Les champs texte se mettent à jour tout de suite, le clic seulement au tour suivant : cliqué **avant** les champs, la civilité était écrasée par eux. Toujours remplir les champs, attendre (~300 ms), puis cliquer la civilité **en dernier** (`content/grandaudition.ts`). L'option « Jour » vide vaut `''` (sur Acuitis : `'no'`).

## Pièges Doctolib connus (ne pas réintroduire)
- **Adresse du patient** (v1.1.12) : certains centres la demandent dans le formulaire de réservation, en trois cases `#address`, `input[name="zipcode"]` (identifiant généré, du type `input-5` : toujours chercher par `name`) et `#city`. La rue vient du champ « Adresse » de la Piste (`lireLieu` : tout ce qui précède le code postal) ; `Fiche.rue`, et la fiche mémorisée pour Doctolib garde rue / code postal / ville (`pushRecent` ne retire plus que le partenaire et son adresse). Attention aux deux sens d'« adresse » : `Fiche.adresse` = adresse du **partenaire** (Opportunité), `rue`/`codePostal`/`ville` = celle du **patient**.
- `/search/availabilities.json` : les listes se passent en **`agenda_ids[]=1&agenda_ids[]=2`** (idem `practice_ids[]`). Avec des virgules, Doctolib répond **400 « agenda_ids: must be an array »** dès qu'un centre a plusieurs agendas — un centre à agenda unique passait, d'où un bug invisible en test (v1.0.38). Tout passe par `paramsCreneaux()` dans `doctolib.ts`.
- `start_date_time` doit être une heure **locale avec décalage** (`2026-09-26T16:00:00+02:00`), pas un `Z`.

### Autorisation du dossier
Le navigateur oublie l'autorisation d'écrire dans le dossier dès que le panneau se ferme, et rien ne permet de la redonner sans un clic de l'utilisateur. Le bandeau ne sort donc **que s'il y a quelque chose à copier** : `cockpit-dossier-ecrit` (localStorage) garde la date des données au moment de la dernière écriture réussie, et le bandeau apparaît quand `data.updatedAt` la dépasse — ouvrir et fermer le panneau sans rien changer ne demande plus rien (v1.0.41). Il reste masquable définitivement par **Ne plus demander** (`cockpit-dossier-silence`), et l'autorisation se redonne quand on veut depuis Réglages. Les données, elles, sont **toujours** écrites dans le navigateur, autorisation ou pas.

**Écriture refusée (v1.1.6).** Autorisation accordée mais écriture impossible (fichier en lecture seule, ouvert ailleurs, dossier déplacé) : `ecrireDossier` renvoie `blocked`, jamais `synced`, et la date d'écriture n'est pas posée. Bandeau « Cockpit n'arrive pas à écrire cockpit.json » avec **Réessayer**, affiché même avec « Ne plus demander » ; Réglages dit « écriture refusée ». Ne jamais réintroduire `writeText(...).catch(() => {})` : c'est ce qui a laissé le fichier de Benjamin trois semaines en retard pendant que le panneau affichait « synchronisé ».

**Fichier partagé par plusieurs Cockpit (v1.1.11).** Benjamin fait tourner quatre Cockpit (Edge et Chrome, version perso et version d'équipe) sur le même `cockpit.json`. À chaque écriture réussie, le dernier état commun est gardé (`cockpit-base` dans `chrome.storage.local`, avec le nom du dossier). Au chargement ou à « Autoriser » : fichier identique à la base → la copie du navigateur fait foi ; fichier plus récent que la base → **fusion à trois** (`storage/sync.ts`) : ce qui n'a changé que d'un côté l'emporte, suppressions comprises ; changé des deux côtés → la copie la plus récente gagne ; listes à `id` élément par élément, autres listes (phrases, ventes, fiches de paie) par valeur, donc une vente passée de CAT 1 à CAT 2 ne se double plus ; modifié ici et supprimé ailleurs → gardé. Sinon (premier échange, autre dossier, vieille copie remise à la main, plus ancienne que la base) → simple réunion `mergeData`, jamais de perte. Toute version qui diffère du fichier est datée de maintenant, pour que les autres Cockpit la voient plus récente que leur base. L'import d'un fichier reste une réunion (`doImport`).

**Rappel de sauvegarde (v1.1.7).** Dossier en pause + changements à copier + dernière écriture réussie vieille de `RETARD_JOURS` (7) jours ou plus : bandeau « Ta dernière sauvegarde date d'il y a N jours » (Mettre à jour / Plus tard = masqué 24 h, `cockpit-rappel-reporte`), **même avec « Ne plus demander »** — la copie du navigateur disparaît si la carte Cockpit est retirée d'Edge. Réglages affiche la date de la dernière sauvegarde. Les trois bandeaux du dossier (pause, écriture refusée, rappel) sont enchaînés dans un seul bloc `… ) || … && (` : c'est ce qui permet au correctif de passer sur `classique` sans conflit (les lignes autour diffèrent entre les deux dispositions).

## Données
`AppData` (voir `model.ts`) : `reglages`, `anamnese {situations, textes ({{resume}} = emplacement du résumé), phrases}`, `chatPartenaire`, `templates`, `categories`, `ventes` (plus affiché ici, mais **gardé** dans les données et les fusions : le même `cockpit.json` peut servir à Cockpit Benjamin). Les signatures des Réglages sont converties au chargement (`variabiliserSignatures`) : un nom ou un téléphone écrit en dur devient `{{nom_conseiller}}` / `{{tel_conseiller}}` — nom reconnu dans n'importe quel ordre de ses mots et sans tenir compte de la casse, téléphone comparé sur ses seuls chiffres (espaces, points, emoji, +33 indifférents), toujours en mot ou nombre entier (v1.1.3). Même conversion, au chargement, pour les **modèles de mail/SMS** (corps, objet, SMS accompagnateur) et les **textes du Chat partenaire** (`variabiliserTextes`, v1.1.5) : le rendu ne change pas pour soi, mais un modèle partagé signe du nom de chacun, et un nouveau modèle reprend la signature **telle quelle, variables comprises** — un modèle partagé signe du nom de chaque collègue (v1.0.49). Variables de texte : `{{nom}}`, `{{date}}`, `{{heure}}`, `{{nom partenaire}}`, `{{adresse}}`, `{{nom_conseiller}}`, `{{tel_conseiller}}`, `{{email_conseiller}}`, `{{titre_conseiller}}` ; formes `patient(e)`, `il(elle)`, `conseiller(ère)` résolues par `resolveGenre`.
Toute réunion de données passe par `mergeData` / `mergeVentes` / `mergePartage` (union, jamais de perte) ; l'échange avec le dossier, lui, passe par la fusion à trois quand le dernier état commun est connu (voir « Fichier partagé par plusieurs Cockpit »). **Même conseiller** (`memePersonne` : mots du nom, ordre et casse libres) : `mergeData` complète les réglages texte vides depuis l'autre copie — deux navigateurs, dossier, import de son propre fichier (v1.1.10). Un fichier de collègue ne touche jamais aux Réglages (`doImport`). Un mot du nom collé à `{{nom_conseiller}}` (« Magnier {{nom_conseiller}} », reste d'une ancienne conversion) est retiré au chargement (`motifDoublonNom`). Sous l'aperçu d'Anamnèse, Mails et Chat partenaire, `VariablesVides` dit quand une variable du conseiller utilisée est vide dans les Réglages — sans ça, `composeComment` retire la ligne sans rien dire.

## Publier une version (chef d'orchestre uniquement)
**Outil (depuis le 2026-10-02)** : un correctif commun aux deux dispositions se publie d'un coup dans les trois versions avec `scripts/publier-trois-versions.sh <commit> <version-fusion> <version-classique> <version-perso> <dossier-textes>` (nouveau design → classique → Cockpit Benjamin, release publique à deux zips, copies dans `Extensions installees`). `scripts/conflits-perso.mjs` résout les conflits habituels du report dans Cockpit Benjamin (nom/version 2.x, documentation). Benjamin veut chaque correctif **dans les trois versions**, et rien ne part chez lui sans son feu vert. Arrêter tout serveur de test (`vite`, `esbuild`) avant `npm ci` dans le dossier principal : un `esbuild.exe` verrouillé fait échouer `npm ci` et vide à moitié `node_modules`.

1. `npx tsc --noEmit` puis `npm run build`.
2. Monter `version` dans `public/manifest.json` et `npm pkg set version=X.Y.Z`.
3. `main` est protégé : commit sur une branche `chore/vX.Y.Z`, `gh pr create`, `gh pr merge --squash --delete-branch`, puis `git checkout main && git pull`, `git tag vX.Y.Z && git push origin vX.Y.Z`.
4. Vérifier `gh run list --repo Benjamin-Mag/cockpit-audibene` : Release (zip) en succès.
5. **Copier la version chez Benjamin** : `cp -r dist/. "../Extensions installees/Cockpit Audibene/"` (et, depuis le dépôt Cockpit Benjamin, vers `../Extensions installees/Cockpit Benjamin/`). Toutes ses extensions non empaquetées vivent dans `Documents\Claude\Projects\Extensions installees\` — plus rien dans Téléchargements depuis le 2026-09-26. Il n'a plus qu'à faire ↻ dans `edge://extensions`. Edge lie une extension à son chemin : ne jamais déplacer ces dossiers.
6. **Mettre les zips à disposition des collègues** : ce dépôt est **privé** depuis le 2026-09-26. Construire **les deux dispositions** — `npm run zip` sur `main` (Fusion → `cockpit-audibene.zip`) et sur un worktree de `classique` (renommer en `cockpit-audibene-classique.zip`) — puis
   `gh release create vX.Y.Z --repo Benjamin-Mag/cockpit-audibene-install --latest cockpit-audibene.zip cockpit-audibene-X.Y.Z.zip cockpit-audibene-classique.zip cockpit-audibene-classique-A.B.C.zip`.
   Le dépôt public `cockpit-audibene-install` (dossier `Projects/Page installation Cockpit`) ne contient **que** la page d'installation et les zips : jamais de code, jamais de journal.
   Lien unique pour les collègues : https://benjamin-mag.github.io/cockpit-audibene-install/
7. Reporter dans Cockpit Benjamin **depuis `main`** (`git fetch upstream && git merge upstream/main`, version 2.x ; depuis le 2026-10-20) et remettre la branche `design/essai` au niveau si elle sert.
## Travailler en équipe
- Un agent = une branche `feature/<chantier>` dans son propre worktree (`git worktree add`), jamais dans le dossier principal.
- Avant de commencer : `git fetch && git rebase origin/main` ; petits commits ; `npx tsc --noEmit` vert.
- Fin de tâche : `git push -u origin feature/<chantier>`, `gh pr create` (titre + ce qui change + comment tester), puis message au chef d'orchestre avec : résumé, fichiers touchés, comment tester sur Salesforce, points d'attention, questions.
- Ne pas modifier `CLAUDE.md`, `README.md`, les workflows ni la version : proposer les changements dans le rapport.
